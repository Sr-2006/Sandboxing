AUTO-SRE PLATFORM — FINAL END-TO-END FEDERATION & DEMO PLAN
================================================================
Version: 2026-08-18
Goal: Four developers can implement separate phases on separate laptops, integrate them with low latency and low coupling, and still have a one-laptop fail-safe demo path.

================================================================
1. FINAL ARCHITECTURAL DECISION
================================================================

Use THREE distinct mechanisms, each for the job it is best at:

1) GitLab + CI
   Purpose:
   - Source control
   - Phase ownership
   - Contract/schema validation
   - Integration testing
   - Distribution of validated build/data artifacts

2) Tailscale private mesh (or direct LAN when all laptops are on the same Wi-Fi)
   Purpose:
   - Live private laptop-to-laptop communication during development
   - Stable machine identity / private addressing
   - Avoid putting Cloudflare Quick Tunnels in every internal service call

3) Cloudflare Tunnel
   Purpose:
   - Public judge/demo ingress only
   - Expose the frontend/API gateway/dashboard when external access is required
   - Do NOT use Quick Tunnels as the internal Phase 1 -> Phase 2 -> Phase 3 -> Phase 4 backbone

4) Single-laptop assembly mode
   Purpose:
   - The authoritative judging/demo runtime
   - All services run on one integration laptop with Docker Compose/local networking
   - Removes dependence on four laptops, four Wi-Fi links, or four tunnels during judging


THE SYSTEM SHOULD HAVE TWO OPERATING MODES:

A. FEDERATED DEVELOPMENT MODE
   Laptop A -> Phase 1
   Laptop B -> Phase 2
   Laptop C -> Phase 3 + Ollama
   Laptop D -> Phase 4

   Communication:
   LAN if available
        else
   Tailscale private mesh

B. LOCAL ASSEMBLY / DEMO MODE
   One integration laptop runs:
   - Phase 1
   - Phase 2
   - ChromaDB
   - Phase 3
   - MCP
   - Ollama
   - Phase 4
   - RabbitMQ
   - PostgreSQL
   - Redis
   - Observability stack
   - Frontend/API gateway

   Communication:
   Docker network / localhost only

The local assembly mode is the judging path.
The federated mode is the team-development and optional distributed-system demo path.


================================================================
2. WHY THE EXISTING DESIGN SHOULD BE REFINED, NOT REWRITTEN
================================================================

The existing repository already has several correct architectural choices:

- Each laptop owns one phase.
- GitLab is the integration backbone.
- Phase branches merge only after CI/contract validation.
- Phase 1 produces unified_master_dataset.json.
- The validated merged dataset can move as a Git artifact.
- Phase 2 therefore does not need Laptop A to remain online just to consume the packaged dataset.
- Heavy workloads are not meant to be duplicated across all laptops.
- The repository already contains a one-laptop "assembly host" demo procedure.

Therefore:

DO NOT replace the whole architecture.

KEEP:
- GitLab flow
- CI contract gates
- Phase ownership
- Phase 1 artifact packaging
- Single-machine assembly demo
- ChromaDB
- Ollama
- RabbitMQ
- Prometheus / Grafana / Jaeger / OpenTelemetry

CHANGE:
- Internal live communication strategy
- Event transport for new live incidents
- MCP transport
- Failure handling
- Service discovery
- Demo/public ingress strategy

Tailscale attempts direct peer-to-peer connectivity between devices and falls back

During integration, record whether paths are:
- direct
- peer-relayed
- DERP-relayed

Direct paths are preferred.

API Gateway
      |

WHY QUICK TUNNELS SHOULD NOT BE THE CORE BUS:

Current Cloudflare documentation states that TryCloudflare Quick Tunnels:
- are intended for testing/development
- have no uptime SLA
- use random trycloudflare.com hostnames
- have a 200 in-flight request limit
- do not support Server-Sent Events (SSE)

So they are useful for temporary public exposure, but not ideal as the internal
nervous system of a multi-stage distributed application.

7. END-TO-END INCIDENT FLOW
================================================================

STEP 1 — TELEMETRY COLLECTION
Laptop A / Phase 1

Inputs:
- Docker states
- CPU
- memory
- stdout/stderr logs
- traces
- metrics
- topology

Pipeline:
Docker telemetry
   ->
Drain3 parsing / clustering
   ->
normalization/masking
   ->

   ->
incident object


STEP 2 — CLUSTERING / OCCURRENCE AGGREGATION
Phase 1 already groups events by failure mode / cluster.

Do not create a completely new dedup subsystem just because the architecture is
being changed.

The new live publisher should publish meaningful incident updates, not every raw
log line.

Example publication rule:

Publish when:
- a new incident cluster appears
- severity changes
- priority materially changes
- service health materially changes
- a recurrence threshold is crossed

Do not publish for every identical log line.

If Phase 4 is:

- timed out
- unreachable
- returns malformed output
- crashes

    |
    v

    |
    v

    |
    v

    |
    v

================================================================
9. LATENCY STRATEGY
================================================================

Do not optimize the wrong thing.

The slowest portion of this system is likely to be AI inference/debate, not a
single transfer of the ~343 KB packaged dataset.

Therefore optimize in this order:

1. Reduce number of LLM calls.
2. Cache repeated RCA results.
3. Cache deterministic/semantic memory lookups.
4. Avoid repeated embeddings for identical fingerprints.
5. Keep Ollama and the agent loop local.
6. Run independent context fetches concurrently.
7. Keep live messages small.
8. Reuse HTTP connections.
9. Use direct LAN/Tailscale paths rather than public reverse-proxy hops.
10. Optimize serialization/network payload size only after measuring it.

================================================================
11. CONCURRENCY
================================================================

Fetch independent context in parallel.

BAD:

topology
  then
metrics
  then
logs
  then
history


BETTER:

            +--> topology ----+
            +--> metrics -----+
incident -->+--> logs --------+--> aggregate context
            +--> history -----+
            +--> traces ------+


Use asyncio.gather or equivalent for independent I/O.

This changes wait time from approximately:

A + B + C + D

toward:

max(A, B, C, D)


================================================================
12. TIMEOUTS AND FAILURE POLICY
================================================================

Every inter-phase call/event workflow needs a finite deadline.

Suggested starting values, to be tuned by measurement:

Phase 2 enrichment:
3 seconds soft target

Phase 3 AI:
model-dependent; set a hard application deadline

Phase 4 veto:
2 seconds target

External public request:
do not let it wait indefinitely for the whole pipeline


DEGRADATION RULES:

Phase 1 down:
- no new telemetry
- existing historical/demo data remains viewable

Phase 2 down:
- Phase 3 may perform telemetry-only RCA
- mark memory_context_available=false

Phase 3 down:
- no AI remediation
- incident remains open

Phase 4 down:
- NO execution
- recommendation-only / human review

RabbitMQ down:
- producers spool/retry locally where practical
- do not silently lose actions

Ollama down:
- Phase 3 marks inference unavailable
- never fabricate RCA output


================================================================
13. RETRIES
================================================================

Use bounded exponential backoff.

Example concept:

attempt 1
wait ~250 ms

attempt 2
wait ~500 ms

attempt 3
wait ~1 s

then:
dead-letter / degraded state

DO NOT perform infinite retries.
